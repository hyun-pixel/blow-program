# BLOW MVP 결정 004 — 관리자 MFA

> 확인일: 2026-09-09
> 상태: 사용자 승인 완료
> 확정안: Google Authenticator를 기본 안내 앱으로 사용하는 TOTP 방식
> 적용 대상: BLOW 관리자와 Supabase 조직 구성원

## 1. 결정 대상

회원, 이용권, 기기 등록과 계정 상태를 다루는 관리자 계정을 비밀번호 탈취로부터 보호할 두 번째 인증 방식을 정한다.

일반 BLOW 사용자는 MVP의 의무 MFA 대상에 포함하지 않는다. 관리자 권한이 있는 계정과 데이터베이스에 접근할 수 있는 Supabase 조직 계정에는 MFA를 의무 적용한다.

## 2. 확정안

시간 기반 일회용 비밀번호인 TOTP를 사용한다.

- 설정 화면에서는 “Google Authenticator 등 인증 앱”으로 안내한다.
- Google Authenticator를 기본 예시로 제공하되 특정 앱에 종속시키지 않는다.
- Microsoft Authenticator, 1Password와 같은 표준 TOTP 앱도 사용할 수 있게 한다.
- 문자와 이메일 인증번호는 관리자 MFA 수단으로 사용하지 않는다.
- TOTP는 Supabase Auth가 제공하는 등록, 확인과 해제 API를 재사용한다.

Google Authenticator는 별도 문자 발송비가 없고 인터넷 연결이 끊겨도 코드를 생성할 수 있다. Supabase의 TOTP MFA는 모든 프로젝트에서 기본 활성화되며 별도 사용료가 없다.

## 3. 보호 범위

### BLOW 관리자 화면

관리자는 다음 두 조건을 모두 만족해야 한다.

1. 데이터베이스에서 관리자 역할을 가진 계정이다.
2. 현재 세션이 MFA 인증을 완료한 `aal2` 상태다.

화면에서 관리자 메뉴만 감추지 않는다. 관리자 API와 Supabase Row Level Security 정책에서도 역할과 `aal2`를 다시 검사한다.

### Supabase 관리 화면

- 프로젝트 소유자와 개발 구성원은 각자의 Supabase 계정에 TOTP를 등록한다.
- Supabase Pro 조직 설정에서 `Require MFA to access organization`을 활성화한다.
- 공유 관리자 계정을 만들지 않고 사람마다 별도 계정을 사용한다.
- 개인 액세스 토큰은 MFA 강제 대상과 별개이므로 필요한 토큰만 발급하고 정기 교체한다.

## 4. 관리자 등록과 로그인 흐름

### 최초 등록

1. 최고 관리자가 관리자 계정을 수동으로 만든다.
2. 관리자가 이메일과 비밀번호로 처음 로그인한다.
3. 관리자 기능을 보여주기 전에 TOTP 등록을 강제한다.
4. 화면의 QR 코드를 인증 앱으로 스캔한다.
5. 인증 앱의 6자리 코드를 입력한다.
6. 확인 성공 후 세션이 `aal2`가 되어야 관리자 기능을 사용할 수 있다.

관리자 공개 회원가입과 초대 링크만으로 관리자 권한을 부여하는 기능은 만들지 않는다.

### 이후 로그인

1. 이메일과 비밀번호를 확인한다.
2. 등록된 인증 앱의 6자리 코드를 확인한다.
3. `aal2` 세션에만 관리자 화면과 API 접근을 허용한다.

## 5. 분실과 복구

Supabase의 프로젝트 사용자 MFA는 현재 복구 코드를 제공하지 않고 계정마다 여러 인증 수단을 등록할 수 있다. 관리자 잠금을 방지하기 위해 다음 기준을 적용한다.

- 관리자마다 주 인증 수단과 예비 TOTP 수단을 각각 등록한다.
- 두 수단은 가능하면 서로 다른 기기 또는 독립적으로 보호되는 인증 앱에 둔다.
- QR 코드, TOTP 비밀키와 6자리 코드는 화면 캡처, 이메일 또는 메신저로 공유하지 않는다.
- 이메일 링크만으로 MFA를 해제하지 않는다.
- 두 인증 수단을 모두 잃은 경우 최고 관리자가 본인 확인 후 수동으로 초기화한다.
- 초기화 대상, 처리자, 시각과 사유를 감사 기록에 남긴다. TOTP 비밀키와 실제 코드는 기록하지 않는다.

자체 복구 코드 기능은 MVP에서 만들지 않는다. 보안 키와 패스키는 피싱 방어에 더 강하지만 Supabase Auth의 기본 두 번째 인증 수단이 아니므로 추후 검토한다.

## 6. 보안 기준

- TOTP QR 코드와 비밀키는 등록 순간에만 보여주며 애플리케이션 데이터베이스나 로그에 복사하지 않는다.
- 인증 실패 횟수를 제한하고 반복 실패를 보안 기록에 남긴다.
- 관리자 권한 부여, MFA 초기화, 이용권 변경과 기기 제한 해제는 감사 기록 대상이다.
- 관리자가 권한을 잃으면 활성 세션과 관련 토큰을 폐기한다.
- 관리자 세션은 일반 사용자보다 짧게 유지하고 장시간 미사용 시 다시 로그인하게 한다.
- 관리자 권한과 MFA 여부를 프런트엔드 값만 믿지 않고 서버와 데이터베이스에서 검증한다.
- Supabase와 Google 계정에도 강한 비밀번호와 MFA를 적용한다.

## 7. 비용과 운영 영향

- TOTP 생성 자체에는 발송 비용이 없다.
- 문자 발송 사업자와 전화번호 수집이 필요하지 않다.
- Supabase 조직 전체 MFA 강제 기능은 Pro, Team과 Enterprise 요금제에서 제공된다. BLOW는 이미 Pro 운영안을 선택했다.
- 관리자 휴대폰 분실 시 복구 절차를 직접 수행해야 하므로 최소 두 명의 책임자를 지정하는 것이 안전하다.

## 8. 완료 기준

- MFA-01: 관리자 최초 로그인에서 TOTP 등록 전에는 관리자 기능을 사용할 수 없다.
- MFA-02: 비밀번호만 확인된 `aal1` 세션은 관리자 화면, API와 데이터에 접근할 수 없다.
- MFA-03: TOTP까지 확인된 `aal2` 관리자만 보호 기능에 접근한다.
- MFA-04: 일반 사용자 계정은 관리자 기능에 접근할 수 없다.
- MFA-05: 주 인증 수단을 사용할 수 없을 때 등록된 예비 수단으로 로그인할 수 있다.
- MFA-06: MFA 초기화와 관리자 권한 변경이 감사 기록에 남는다.
- MFA-07: QR 코드, 비밀키와 실제 인증번호가 저장소, 로그와 오류 화면에 남지 않는다.
- MFA-08: Supabase 조직 구성원 전원에게 MFA 강제가 적용된다.
- MFA-09: MFA 실패를 반복해도 관리자 존재 여부나 내부 정보를 노출하지 않는다.
- MFA-10: 로그아웃 또는 권한 회수 후 이전 관리자 세션으로 접근할 수 없다.

## 9. 실제 구축 시 순서

1. 사용할 관리자 이메일과 최고 관리자 책임자를 정한다.
2. Supabase 조직 계정에 TOTP를 등록하고 조직 MFA 강제를 활성화한다.
3. BLOW 관리자 역할과 감사 기록 구조를 만든다.
4. 관리자용 TOTP 등록, 확인과 예비 수단 관리 화면을 만든다.
5. 관리자 라우트, API와 RLS에 역할 및 `aal2` 검사를 적용한다.
6. 휴대폰 분실, 예비 수단, 강제 초기화와 권한 회수 시나리오를 테스트한다.

## 10. 아직 실행하지 않는 작업

- 실제 관리자 계정 생성
- 실제 휴대폰에 TOTP 등록
- Supabase 조직 MFA 강제 설정 변경
- 관리자 권한과 RLS 정책 구현
- 운영 계정의 MFA 초기화 시험

이 작업은 Supabase 프로젝트를 만들고 관리자 기능 구현을 시작할 때 진행한다.
